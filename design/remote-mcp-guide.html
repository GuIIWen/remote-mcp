remote-linux MCP：让 AI Agent 直接操作内网 Linux

一个跑在 Windows 本机的常驻小服务。它替 AI 编码助手打通“本机 → 跳板机 → 内网机器 / 计算节点 / 容器”这条链路，把远端的读文件、改代码、跑命令、搜索变成和本地一样的工具调用。跳板机只登录一次（需要验证码的环境也只输一次），远端什么都不用装。

1 次每次启动只登录一次跳板机，所有会话复用
0 安装跳板机和目标机不装任何组件
3 种路由跳板机隧道 / 跳板机代跑 / 直连
9 个工具语义对齐 Claude Code 内置的 Read / Edit / Grep

没有它：AI 在“墙外”干着急

  • 代码在内网机器上，AI 只能看到本机
  • 手写 ssh host "..."，引号层层转义
  • 每条命令都要重新经跳板机握手，有验证码的环境每次都要输
  • 计算节点的私钥只在跳板机上，本机连不过去
  • 文件得来回复制粘贴给 AI 看
➜

有了它：对 AI 来说，远端就是“本地”

  • “帮我看下 dev1 上的训练日志” —— 直接读
  • edit_file 精确替换并原子写入
  • 一条跳板机长连接，后续调用不再认证
  • hop 路由让跳板机代跑 ssh，连容器里都能进
  • 多个会话、多个 Agent 共用一组连接

02背景与痛点

开发者在 Windows 上用 AI 编码助手，但代码的编译、运行、调试都在另一个网络里的 Linux 机器上，比如公司内网、机房集群或云上的私有网络。本机通常连不到这些机器，要先登录一台跳板机（堡垒机、登录节点或网关机）再跳转过去。

🧱要经过跳板机中转

目标机器只能从跳板机访问。跳板机的认证方式因环境而异：有的只用 SSH 密钥，有的还要 TOTP 验证码或动态口令。每条命令都重新经跳板机登录一次，慢且繁琐；有二次验证的环境基本没法用。

🪟Windows 没有 ControlMaster

Linux/macOS 上可以用 OpenSSH 的 ControlMaster 复用连接，Windows 版 OpenSSH 不支持，没法靠 ssh 配置解决。

🚫不想在远端装东西

节点常常没有 root 权限、数量多且环境各异，还可能被重装、重建。每台都部署一个服务，安装、升级和审计成本都很高；刚交付的新节点上也还什么都没有。所以工具只依赖远端自带的 sshd、bash 和 coreutils。

🔑节点类型五花八门

有的走跳板机、有的本机能直连（密码或密钥）、有的计算节点只有跳板机持有私钥、有的服务跑在 docker 容器里。

设计目标：给 AI 一个统一的远端工作区

目标不只是“能 ssh 上去”，而是让 AI Agent（Claude Code、Codex 或其他支持 MCP 的 Agent）把远端的一批 Linux 节点当成本地工作区来用：读文件、改代码、执行命令、搜索内容，还能在多个节点之间对比和批量操作。

🔍多节点对比

“dev1 能跑、dev2 不行，帮我找差异”：AI 在两个节点上分别读取配置、查看驱动和依赖版本、环境变量和日志，然后对比给出结论。

📋批量巡检

一句话检查所有节点的磁盘、显卡、docker、进程和服务状态，汇总成一张表。节点都在连接池里，不用逐台登录。

🚀部署与运维

把节点初始化、推理服务部署等流程写成 Skill，AI 在多个节点上按步骤执行并验收，不可逆操作前先让用户确认。

🧭屏蔽网络差异

无论节点是经跳板机隧道、由跳板机代跑 ssh、本机直连还是在容器里，AI 都只需要传 host="..."。

✍️本地化的工具语义

Read / Edit / Grep / Glob 的用法照搬，写文件是原子操作。AI 不需要学新工具，也不用拼引号转义。

🛡️可控可审计

白名单限定可访问的节点，命令和写操作记录到本地审计日志；私钥、密码不离开本机，远端不装任何组件。

为什么选“本地 HTTP Daemon + asyncssh 连接池”

方案跳板机登录频率远端依赖主要问题
PowerShell 里直接 ssh host "..."每条命令无无连接复用、引号转义困难、每次重新握手
stdio 模式，每个会话拉起一个 MCP 进程每个会话无进程随会话重建，跳板机连接无法复用
在远端部署 MCP Server按需每台都要装维护成本高、环境差异大、无法统一审计
本地常驻 HTTP Daemon（本项目）仅启动时一次无需要一个保持前台的窗口
核心思路
跳板机连接只建一次并常驻；之后访问目标机用 asyncssh.connect(target, tunnel=bastion_conn) 在这条已认证的连接上开 direct-tcpip 隧道，不再重复登录跳板机。Daemon 以 Streamable HTTP 暴露 MCP，多个客户端会话共享同一个连接池。
关于 TOTP
本文后面说的“输入 TOTP”，泛指跳板机登录时的交互式验证（keyboard-interactive，比如验证码、动态口令）。如果你的跳板机只用密钥认证，启动和重连时都不会弹出提示，相关注意事项可以忽略。

03整体架构

所有逻辑都在本机：客户端只和 127.0.0.1:8765 说话，Daemon 负责连接、路由、超时、重试和审计。

模块分工

模块负责不负责
tools.py定义 MCP 工具签名；路径解析（default_cwd、~）；拼远端命令；输出截断；审计与密码脱敏不直接持有 SSH 连接
pool.py维护跳板机/目标机连接；按 via 分派路由；并发控制；远端 timeout 包装；断线诊断与重试；心跳；配置校验与热更不了解 MCP 协议和工具语义
daemon.py加载并校验配置；启动时预连接密码节点、登录跳板机；启动心跳和 HTTP 服务不含业务逻辑
setup_ssh_keys.py独立小工具：用密码登录直连节点，批量装公钥、记录指纹、验证免密不经过跳板机，不参与 daemon 运行

hop 路由的细节

hop 节点在跳板机上实际执行的命令形如：

ssh -o BatchMode=yes -o ControlMaster=auto \
    -o ControlPath=~/.ssh/remote-mcp-%C -o ControlPersist=10m \
    [-p <port>] [-l <user>] nmz01 '<timeout 包装后的命令>'
  • BatchMode=yes：禁止任何交互提示。缺密钥或 host key 不对时 ssh 以 255 退出，Daemon 将其包装为 HopSSHError 并附带 stderr，而不是卡住。
  • ControlMaster：在跳板机这一侧复用到节点的连接，连续调用不用每次重新握手。
  • 容器模式：配置 container 后，命令再包一层 docker exec -i [-u 用户] 容器 bash -c …，default_cwd 和所有路径都是容器内路径。同一个 node 可以配多个段对应不同容器。

05一次工具调用的全过程

以 exec(host="dev1", command="make -j8", cwd="src") 为例：

tools.py① 审计

写入 audit.jsonl（host / action / 命令）

tools.py② 拼路径

cd default_cwd && cd src &&，与其它工具的相对路径规则一致

pool.py③ 白名单 + 路由

检查 [hosts] allowed，按 via 选连接方式

pool.py④ 取连接

复用池中连接；空闲超过 120 秒先探活，失效就重连

pool.py⑤ 超时包装

timeout -k 5 N bash -c '…'，由远端负责杀进程

pool.py⑥ 执行

信号量限流；客户端另有 N+15 秒兜底

tools.py⑦ 返回

exit_code / stdout / stderr，超过 30K 字符时保留首尾

06工具一览

工具语义刻意贴近 Claude Code 内置工具，模型不需要学习新概念。左侧带红边的是写操作，会记录审计日志。

list_hosts()

跳板机状态、白名单，以及每个节点的路由、认证方式、连接状态。不含密码。

建议每次会话先调一次
exec(host, command, cwd?, timeout=60)

执行 shell 命令，返回退出码、stdout、stderr。相对 cwd 基于 default_cwd。

≈ Bash
read_file(host, path, offset=1, limit=2000)

按行分页读取，带行号前缀。

≈ Read
write_file(host, path, content)

整文件覆盖，先写临时文件再 rename，保留原权限，跟随软链接。

≈ Write
edit_file(host, path, old_str, new_str, replace_all?)

精确替换；old_str 不唯一时报错并要求补充上下文。

≈ Edit
grep(host, pattern, path?, glob?, context?)

远端有 rg 就用 rg，否则退回 grep -rnE，自动跳过 .git。

≈ Grep
glob_files(host, pattern, base?)

支持 ** 的文件匹配，最多返回 200 条。

≈ Glob
reload_config()

热更 [host.*] 和 [hosts]，不断开跳板机、不重新输 TOTP。失败时保留旧配置。

加节点不用重启
reset_connections()

关闭所有连接，下次调用时重建。会再次触发 TOTP。

连接异常时的手动兜底
路径规则
exec 的 cwd、glob_files 的 base、以及 read_file / write_file / edit_file / grep 的相对路径，都以节点的 default_cwd 为基准解析；~ 和 ~/... 会展开。因此 exec("ls src") 和 read_file("src/a.py") 一定指向同一个目录。

07可靠性设计

跳板机连接一断就要再输 TOTP，所以项目在“保持连接”和“出错时怎么处理”上做了较多设计。

🫀 三层保活

  • SSH keepalive：每 15 秒一次，连续 8 次无响应判定断线（可配置）。
  • 心跳：每 60 秒在已有的跳板机连接上开一个 channel 跑 true，防止跳板机按“channel 无活动”踢人。心跳不会自己重连，所以不会凭空弹出 TOTP。
  • 空闲探活：连接空闲超过 120 秒后，复用前先用 5 秒探测一次，半死连接提前重建。

🔍 断线诊断

断线时在 Daemon 窗口打印连接时长、空闲时长和推断原因，例如：

  • 存活时长是整数（如 ~1h）→ 可能是会话时长上限
  • 空闲时长是整数 → 可能是空闲超时策略
  • exc=None → 对端主动断开
  • keepalive failure → 网络问题

错误处理策略：哪些会重试，哪些不会

情况处理原因
网络断开（ConnectionLost / DisconnectError / OSError）重连并重试 1 次属于可恢复的瞬时故障
认证失败 PermissionDenied不重试重试错误密码可能导致账号被锁；跳板机上还会重复要求 TOTP
建连超时 TimeoutError不重试重试会让等待时间翻倍
命令超时（退出码 124 / 137）报 RemoteTimeout远端 timeout 已经结束了进程
hop 节点 ssh 失败（退出码 255）不重试，报 HopSSHError属于跳板机侧的密钥或配置问题，重试解决不了
edit_file 写成功后断线幂等保护重试时检测到已完成，不会重复替换或误报“未找到”

⚛️ 原子写

先写 .mcp.tmp，再 chmod 和 rename 替换，目标文件只会是旧版本或新版本。保留原权限，写入软链接时修改的是链接指向的文件。

🚦 并发限流

sshd 默认每条连接最多 10 个 channel。每个节点限 8 个并发；所有 hop 节点共用一条跳板机连接，因此合计限 8 个。

🔒 断线隔离

跳板机断线时只清理经它连接的节点，direct 节点不受影响。每个节点有独立的建连锁，互不阻塞。

08安全边界

✅ 已有的防护

  • 只监听 127.0.0.1，局域网其它机器访问不到
  • 主机白名单 [hosts] allowed，支持通配符
  • 私钥留在本机，不开 agent forwarding
  • 密码只保存在进程内存中，错误信息会脱敏，list_hosts 和审计日志里不出现密码
  • config.toml / nodes.yaml 已加入 gitignore
  • 容器名、用户名做了字符集校验，避免命令注入
  • direct 节点可配置 known_hosts 校验 host key

⚠️ 需要知道的边界

  • 没有命令黑名单：AI 发出的 rm -rf 会被执行。重要机器请依赖客户端的权限确认，或不要放进白名单。
  • 任何能访问本机 8765 端口的进程都能调用工具（目前没有鉴权）。
  • 客户端如果能修改 config.toml，可以放宽白名单后调用 reload_config 生效。
  • bastion / hop 路由默认不校验 host key。

09使用说明

从零到可用大约 10 分钟。完整说明见 DEPLOY.md。

  1. 安装依赖 本机 PowerShell

    需要 Python 3.11+，推荐用 uv（无需管理员权限）。

    irm https://astral.sh/uv/install.ps1 | iex     # 已装可跳过
cd <REMOTE_MCP_DIR>
uv venv --python 3.11
uv pip install -r requirements.txt

    如果报 No module named 'pywintypes'：运行 & .venv\Scripts\python.exe .venv\Scripts\pywin32_postinstall.py -install。

  2. 填写配置 config.toml

    copy config.example.toml config.toml
    [bastion]
host = "bastion.example.com"
user = "<跳板机用户名>"

[daemon]
port      = 8765
audit_log = "D:/tools/remote-mcp/audit.jsonl"   # 可选

[hosts]
allowed = ["dev1", "nmz01", "nmz01-ctr", "lab3"]

[host.dev1]                  # 经跳板机隧道（默认）
user        = "<远端用户名>"
default_cwd = "<远端家目录>"  # 在远端 echo $HOME 确认

[host.nmz01-ctr]             # 跳板机代跑 + 进入容器
via       = "hop"
node      = "nmz01"
container = "<容器名>"
default_cwd = "/workspace"

[host.lab3]                  # 本机直连
via     = "direct"
address = "192.168.10.23"
user    = "<远端用户名>"
auth    = "key"              # 或 "password"（留空则启动时输入）
default_cwd = "<远端家目录>"

    各字段的说明见 config.example.toml 里的注释。不确定用哪种 via 时，参考 配置选型。

  3. 配置免密登录 一次性

    • bastion 路由：把本机公钥加到跳板机和目标机的 ~/.ssh/authorized_keys（权限 700 / 600）。
    • direct 节点较多时：用脚本批量配置，只要这些机器目前能用密码登录： 
      copy nodes.example.yaml nodes.yaml   # 填 ip / port / 密码
uv run setup_ssh_keys.py nodes.yaml  # 登录 → 记录指纹 → 装公钥 → 验证免密
    • hop 节点：本机不需要做任何事，只需确认在跳板机上 ssh -o BatchMode=yes nmz01 hostname 能直接返回结果。

  4. 启动 Daemon 独立的前台窗口

    cd <REMOTE_MCP_DIR>
uv run daemon.py
# Verification code: ******     ← 输入 TOTP
# remote-mcp listening on http://127.0.0.1:8765/mcp
    注意
    这个窗口要一直保持在前台、可以输入。跳板机断线重连时会在这里再次要求 TOTP，在此之前所有工具调用会一直等待。也不要让 AI 在后台替你启动它，后台没有终端，会卡在输入提示上。

  5. 接入客户端 只需一次

    # Claude Code（用户级，所有项目可用）
claude mcp add --transport http --scope user remote-linux http://127.0.0.1:8765/mcp
    # Codex：~/.codex/config.toml
[mcp_servers.remote-linux]
url = "http://127.0.0.1:8765/mcp"

    其他 Agent（Cursor、Cline、VS Code Agent 模式、基于 Agent SDK 的自研 Agent 等）：Daemon 是标准的 MCP Server，在对应客户端的 MCP 配置里添加同一个地址即可。

    # 支持 Streamable HTTP 的客户端：直接填 URL
http://127.0.0.1:8765/mcp

# 只支持 stdio 的客户端：用 mcp-remote 桥接
command = "npx"
args    = ["-y", "mcp-remote", "http://127.0.0.1:8765/mcp"]

    各客户端的配置文件位置和字段名不一样，以它们自己的文档为准。所有客户端共享同一个 Daemon 和同一组连接，多接一个客户端不会多登录一次跳板机。项目附带的 Skill 是 CC / Codex 的 SKILL.md 格式，其他 Agent 需要把其中的流程改写成各自的规则或提示词。

  6. 验证 在 Agent 里

    依次让 AI 调用：list_hosts（跳板机显示 connected）→ exec(host="dev1", command="pwd")（返回 default_cwd）→ read_file 读取一个已知文件。三步都正常就可以使用了。

→ exec(host="nmz01", command="hy-smi; docker images | head; cat /etc/docker/daemon.json") → exec(host="nmz02", command="hy-smi; docker images | head; cat /etc/docker/daemon.json") → grep(host="nmz02", pattern="error|Error", path="/data0/logs", context=3) 两台的主要差异：nmz02 的驱动版本较旧，有 2 张卡处于 offline 状态，日志中的报错与此对应。建议先在 nmz02 上处理驱动问题。

10配置选型：我的机器该用哪种 via？

从上往下判断，命中第一条就停。

本机能直接 ping 通 / ssh 到这台机器吗？不经过跳板机，网络直接可达
via = "direct"
密码登录也可以；之后建议用 setup_ssh_keys.py 改成密钥登录
能把本机公钥放进这台机器的 authorized_keys 吗？只能经跳板机访问，但你可以登录它并修改自己的 ~/.ssh
via = "bastion"
这是默认值，可以不写 via
只有在跳板机上执行 ssh <节点> 才能登录？典型情况：计算节点，私钥在跳板机上
via = "hop"
如果要在节点上的 docker 容器里工作，另起一段加上 node + container

12常见问题

现象原因与处理
工具调用一直没有返回多半是 Daemon 窗口在等待 TOTP，切过去输入即可
空闲一段时间后又要 TOTP跳板机断开了连接，看 Daemon 窗口的 hint: 判断是会话时长上限、空闲策略还是网络问题
Host '…' is not in the allowed list加入 [hosts] allowed 后调用 reload_config
相对路径找不到文件default_cwd 填错了。家目录不一定是 /home/<用户名>（有的集群是 /public/home/<用户名>），先在远端 echo $HOME 确认
hop 节点报 ssh to … on the bastion failed跳板机自身 ssh 不到该节点，登录跳板机运行 ssh -o BatchMode=yes 节点 hostname 复现
容器节点报 No such container容器名写错或容器未运行；确认跳板机用户在该节点上能不加 sudo 执行 docker
端口被占用修改 [daemon] port，并同步修改客户端里配置的 URL
direct 节点密码错误交互输入最多试 3 次，配置文件中的密码只试 1 次，失败则跳过该节点，不影响其它节点

更多排障项见 DEPLOY.md 第 8 节。

13限制与路线图

当前限制

  • Daemon 必须在前台窗口常驻；窗口被关闭后需要重新启动并输入 TOTP
  • 只支持一台跳板机
  • 只能本机访问，没有鉴权
  • 单次 exec 是同步的，长任务需要自己放后台再轮询
  • 每次 exec 都是新 shell，cd 和环境变量不会保留
  • 容器模式下超时只会结束跳板机上的 ssh/docker 客户端，容器内已启动的进程不一定被结束
  • 不支持二进制文件上传和下载

规划中（TODO.md / 设计文档）

  • 多台并列跳板机：via = "<跳板机名>"，每台单独输入 TOTP
  • 局域网访问：可配置监听地址 + api_key（Bearer 鉴权）；绑定非回环地址但没有 key 时拒绝启动
  • 后台任务：exec(background=True) 用 setsid 后台运行，任务记录（pid / 日志 / 退出码）放在远端，配合 job_status / job_output / job_kill 使用，不依赖 tmux
  • 命令黑名单和只读节点（readonly = true）
  • SFTP 上传和下载、实时 tail 日志
