1. 背景与目标

开发者在 Windows 本机使用 Claude Code（CC）或 Codex，但实际的代码运行、调试、编译工作发生在内网 Linux 机器上。这两个世界之间有一道跳板机墙：所有内网机器只能通过跳板机访问，跳板机要求 TOTP 验证码认证。

目标是让 CC / Codex 能像操作本地文件一样操作远端 Linux，读文件、改代码、执行命令、搜索内容，而不是在 PowerShell 里手写 SSH 命令行。

约束条件

  • 跳板机：标准 sshd，允许 TCP 转发，登录需要 TOTP 验证码
  • 目标机：密钥认证，无需 TOTP
  • 直连节点：一部分机器不走跳板机，本机可以直接通过 ip:port 访问，用户名加密码或密钥/证书登录（见 3.4）
  • Windows 本机：无 ControlMaster 支持（Windows OpenSSH 限制）
  • 远端机器不能安装任何东西
  • 需要同时支持 CC 和 Codex 两个客户端

2. 整体架构

为什么选择「本地 HTTP Daemon + asyncssh 连接池」

方案 TOTP 频率 远端依赖 关键缺陷
PowerShell 直接 ssh host "..." 每次连接 无 Windows 无 ControlMaster；引号转义地狱；每条命令重新握手
CC stdio 每次拉起 MCP 进程 每个会话 无 进程每次重建 SSH 连接，TOTP 无法复用
远端部署 MCP Server 按需 每台机器都要安装 维护成本高；远端环境差异大；无法统一审计
本地 HTTP Daemon（本方案） 仅启动时一次 无 需要保持 Daemon 常驻窗口
ℹ
核心 trick：asyncssh.connect(target, tunnel=bastion_conn)。跳板机连接在 Daemon 启动时建立一次，之后所有目标机通过这条已认证的连接打 direct-tcpip 隧道，TOTP 不再介入。

3. 连接方案：跳板机与直连

3.1 TOTP 认证交互

asyncssh 的 kbdint_challenge_received 回调在跳板机发来 keyboard-interactive 挑战时触发。Daemon 进程在启动时占用一个 PowerShell 窗口，TOTP 提示出现在该窗口，用户输入后连接建立，此后不再需要。

# 认证回调核心逻辑
async def kbdint_challenge_received(self, name, instructions, lang, prompts):
    loop = asyncio.get_event_loop()
    responses = []
    for prompt, echo in prompts:
        sys.stderr.write(prompt); sys.stderr.flush()
        if echo:
            resp = await loop.run_in_executor(None, input)
        else:
            resp = await loop.run_in_executor(None, lambda: getpass.getpass(""))
        responses.append(resp)
    return responses

3.2 连接建立流程

3.3 keepalive 与断线重连

跳板机通常会踢掉空闲连接，须在 SSH 层设置保活：

asyncssh.connect(host,
    keepalive_interval=30,     # 每 30 秒发一次 keepalive
    keepalive_count_max=3,     # 连续 3 次不响应才判定断线
)

当工具调用捕获到 ConnectionLost 或 DisconnectError 时，连接池清空所有目标机连接并重试一次。若跳板机本身也断了，Daemon 窗口会再次提示输入 TOTP，也提供一个 reset_connections 工具手动触发。

3.4 直连节点（不经过跳板机）

有一部分节点本机可以直接访问，不需要经过跳板机，通过 ip:port 加用户名登录，认证方式是密码或密钥/证书。这些节点也纳入同一个连接池管理，工具层的用法保持不变：模型只需要传 host="lab3"，不用关心它走哪条路由。

路由字段 via

每个 [host.<name>] 新增一个 via 字段：

  • via = "bastion"（默认值，不写就是它）：走跳板机隧道，行为和现在完全一样。登录方式是 用户名@节点名，节点名本身就是目标主机名，由跳板机负责解析，因此不用配 address。认证只用密钥免密登录，不需要也不接受 password。
  • via = "direct"：Daemon 直接对 address:port 发起 SSH 连接，不经过跳板机，也不需要 TOTP。认证方式可以是密码，也可以是密钥或证书。

这个字段的设计与 TODO.md 里的多跳板机方案一致：以后 via 的取值可以是某个跳板机的名字，"direct" 作为保留值。现在这样做，将来加多跳板机时配置格式不用再改。

配置示例

[host.dev1]                      # 跳板机节点：songjiajun@dev1，密钥免密
user        = "songjiajun"
default_cwd = "/public/home/songjiajun"

[host.lab3]                      # 直连 + 密钥（可选 OpenSSH 用户证书）

[host.lab4]                      # 直连 + 密码
via         = "direct"
address     = "192.168.10.24"
user        = "songjiajun"
auth        = "password"
password    = "********"         # 明文写在本机 config.toml（已 gitignore）；留空则在 Daemon 启动时提示输入
default_cwd = "/public/home/songjiajun"

认证方式

authasyncssh 参数说明
keyclient_keys=[key]，有 cert 时传 client_keys=[(key, cert)]"证书登录"有两种理解，这里都支持：普通私钥文件，或 CA 签发的 OpenSSH 用户证书（*-cert.pub）。如果私钥设了口令，在启动时提示输入一次。
passwordpassword=...asyncssh 会用这个密码处理 password 认证，也会自动应答只有一个隐藏提示的 keyboard-interactive 认证。有些 sshd 关闭了 PasswordAuthentication 但开着 kbdint，这种情况同样能登录（开发阶段要实测确认）。
⚠
密码存放：直连节点的密码可以明文写在 config.toml 的 password 字段。为此 config.toml 要加进 .gitignore，仓库里只提交不含真实凭据的模板 config.example.toml。password 留空时，Daemon 启动时会用 getpass 提示输入。两种来源的密码最终都只保存在进程内存 _passwords[host] 里，断线重连时直接复用，不会再提示。审计日志、错误信息和 list_hosts 的输出里都不能出现密码。

启动顺序

  1. 读取 config.toml。如果文件不存在，报错并提示“复制 config.example.toml 为 config.toml 后填写”，然后退出。接着校验配置：direct 节点缺少 address 或 auth 不合法时直接报错；bastion 节点如果写了 password 或 address，打印警告并忽略这两个字段。
  2. 找出所有 auth = "password" 且 password 为空的 direct 节点，依次提示输入密码，提示信息带上节点名。
  3. 对每个密码节点做一次验证连接，密码来自配置文件或刚才的输入都算。认证失败（PermissionDenied）时：密码是交互输入的，就重新提示，最多 3 次；密码写在配置文件里的，不重试，直接打印“配置里的密码错误”。两种情况最终都跳过该节点，不阻塞 Daemon 启动。如果是网络不可达或超时，只打印警告，等首次调用时再按需连接。验证成功的连接直接放进连接池。
  4. 只要配置了 [bastion]，就连接跳板机并输入 TOTP，和现在一样。如果所有节点都是 direct，可以省略 [bastion]，Daemon 也不会去连接跳板机。
  5. 启动 HTTP 服务。

密钥节点不做预连接，首次调用时再建连，与现在的 bastion 节点一致。

连接池改动要点

def _route(host) -> str:
    return cfg.get("host", {}).get(host, {}).get("via", "bastion")

async def get_target(host):
    ...                                   # 白名单、host 锁、池内复用 —— 不变
    if _route(host) == "direct":
        hc = cfg["host"][host]            # 直连节点必须在配置里，且必须有 address
        kwargs = dict(port=hc.get("port", 22), username=hc["user"],
            known_hosts=hc.get("known_hosts"), keepalive_interval=30,
            keepalive_count_max=3, connect_timeout=_connect_timeout(),
            client_factory=lambda: _TargetClient(host))
        if hc.get("auth", "key") == "password":
            kwargs["password"] = _passwords.get(host, "")
        else:
            kwargs["client_keys"] = _host_client_keys(host)   # auth=key 时
        conn = await asyncssh.connect(hc["address"], **kwargs)
    else:
        async with _bastion_lock:         # 只有 bastion 路由才碰跳板机锁
            bastion = await _ensure_bastion()
        conn = await asyncssh.connect(host, tunnel=bastion, ...)   # 不变
  • 断线隔离：现在 _BastionClient.connection_lost 会执行 _target_conns.clear()，把直连节点的连接也一起清掉。改成只清理 _route(h) != "direct" 的条目，直连节点不受跳板机断线影响。
  • 认证失败不重试：asyncssh.PermissionDenied 是 DisconnectError 的子类，现在 run() 和 with_sftp() 捕获 DisconnectError 后会重试一次。密码错了会连续尝试两次，可能触发账号锁定；在 bastion 路由上还会导致重复提示 TOTP。因此在 except TimeoutError: raise 旁边再加一条 except asyncssh.PermissionDenied: raise，且必须排在 except (ConnectionLost, DisconnectError, OSError) 之前。
  • 密钥来源：现在目标机统一使用 [bastion] key。改成先看 [host.x] key/cert，没有配置时再回退到 bastion 的 key，最后回退到默认密钥对（_host_client_keys(host)）——这条链对 bastion 路由和 direct 路由的目标机统一生效，不是只有直连节点才这样。
  • 主机名：bastion 路由仍然直接用节点名作为连接的主机名，即 用户名@节点名，由跳板机解析，不引入 address。direct 路由的 address 是必填项，缺失时 Daemon 启动阶段就报错。
  • 其余机制通用：Semaphore(8)、host 锁、远端 timeout 包装、connection_made/lost 身份比较、reset_connections、路径解析规则，直连节点全部沿用。reset_connections 之后，直连节点用缓存的密码静默重连，不会重新提示。
  • 缺少 [bastion] 段：如果某个 bastion 路由的节点被使用，但配置文件里根本没有 [bastion] 段，连接池会抛出清晰的 ConfigError（"no [bastion] section is configured..."），而不是原始的 KeyError。
  • list_hosts：每个节点显示路由（bastion / direct address:port）、认证方式和连接状态。

4. MCP 工具 API

工具语义刻意贴近 CC 内置工具（Read / Edit / Grep），让模型不用学新概念。

list_hosts
列出跳板机状态、白名单，以及每个已配置节点的路由（bastion / direct address:port）、认证方式和连接状态。无参数。
exec(host, command, cwd?, timeout?)
执行 shell 命令，返回 exit_code / stdout / stderr。输出超过 30 KB 时截断首尾各 15 KB。
read_file(host, path, offset?, limit?)
按行号分页读取文件，带行号前缀（类 cat -n）。默认读 2000 行。
write_file(host, path, content)
原子写入：先写 .mcp.tmp，再 posix_rename。保留原文件权限位。
edit_file(host, path, old_str, new_str, replace_all?)
精确替换。old_str 必须在文件中唯一，否则报错，要求增加上下文。与 CC Edit 语义一致。
grep(host, pattern, path?, glob?, context?)
优先用 rg，退回 grep -rn。支持 glob 文件过滤和上下文行数。
glob_files(host, pattern, base?)
用 find 实现，返回最多 200 条路径。
reset_connections
清空连接池，触发跳板机重连。跳板机重启或 TOTP 过期后使用。

输出截断策略

所有工具的文本输出共用同一个截断函数，阈值 30 000 字符：保留头部 15 000 字符 + 截断说明 + 尾部 15 000 字符。这个形状让模型既看到文件开头的 import 和函数签名，又看到末尾的实现细节，比只保留头部更有用。

edit_file 的错误处理

5. 连接生命周期

连接池结构

_bastion_conn: SSHClientConnection | None      # 唯一跳板机连接
_target_conns: dict[str, SSHClientConnection]  # host → 目标机连接
_sems:         dict[str, asyncio.Semaphore]    # host → 并发限制（8）
_bastion_lock: asyncio.Lock                    # 跳板机建连时互斥
_host_locks:   dict[str, asyncio.Lock]         # host → 该目标机建连时互斥（懒创建）

跳板机只有一条连接，所以用单独一把 _bastion_lock 就够了；目标机有多台，如果所有目标机共用一把锁，A 机器正在建连会挡住 B 机器的建连请求，明明两者毫无关系。因此每个 host 各自懒创建一把锁（_host_locks.setdefault(host, asyncio.Lock())），只互斥同一台目标机的并发建连，不同目标机之间互不影响。

并发限制

sshd 默认 MaxSessions 10，每条 SSH 连接最多同时开 10 个 channel。CC 可能并发调用多个工具，超过上限时 sshd 会拒绝新 channel。每个目标机设 Semaphore(8)，留 2 个 channel 余量给 SFTP 操作。

connect_timeout：建连超时

config.toml 的 [daemon] connect_timeout（默认 20 秒）传给每一次 asyncssh.connect(...)（跳板机和目标机都用同一个值），对应 asyncssh 自己的 connect_timeout 参数——超过这个时间连接还没建立就直接抛 TimeoutError。run()/with_sftp() 里 except TimeoutError: raise 专门写在 except OSError 之前，确保建连超时不会被断线重试逻辑当成普通断线吞掉再重试一次（Python 3.11 起 TimeoutError 是 OSError 的子类，顺序反了会导致误吞）。

远端命令的 timeout 包装

exec/read_file/grep/glob_files 等工具执行远端命令时，实际发给 shell 的不是原始命令本身，而是 timeout -k 5 {N} bash -c {quoted}——N 是工具调用时传入的 timeout（默认 60 秒）。这是因为单纯 SSH 层面 terminate() 或关闭 channel，并不保证杀掉远端已经 fork 出去的子进程（没有分配 pty 时尤其如此）；用远端自带的 timeout 命令，由远端内核负责在超时后先发 SIGTERM，5 秒后还没退出再补一个 SIGKILL（-k 5），可靠得多。退出码 124（SIGTERM 超时）或 137（SIGKILL，128+9）都被识别为"远端超时"而不是命令本身失败。客户端这一侧再叠加一层 asyncio.wait_for(..., timeout=N+15) 作为兜底——多给 15 秒余量，用来覆盖远端 timeout 命令本身的调度延迟和网络往返，避免远端已经如期杀掉进程、只是回包慢了一点就被客户端误判成连接卡死。如果目标机上根本没有 timeout 命令（command -v timeout 探测失败），会退化成直接 bash -c 执行、不做远端强制超时，这时全靠客户端的 wait_for 兜底——一旦触发就只能断连了事，不保证远端进程被杀掉，纯属兼容极端精简环境的降级路径。

Daemon 的传输方式：Streamable HTTP vs stdio

CC 和 Codex 都支持 Streamable HTTP（/mcp 端点，取代旧的 SSE 传输）和 stdio 两种传输。本方案选 Streamable HTTP：

  • 进程在 Daemon 窗口常驻，多个 CC / Codex 会话共用同一组连接
  • stdio 模式下 CC 每个会话拉起一个新进程，TOTP 无法复用
  • Streamable HTTP 只监听 127.0.0.1，不暴露到局域网

Daemon 崩溃或重启

CC 的 MCP 客户端会在工具调用失败后自动重试连接。Daemon 重启后，daemon 启动时会立即触发跳板机重连（再次输 TOTP），目标机连接随后在首次调用时按需重建。

6. 安全策略

主机白名单

在 config.toml 的 [hosts] allowed 列表里配置允许访问的主机，支持通配符（如 10.0.*）。留空表示不限制，生产环境建议显式配置。

密钥管理

⚠
不要开启 agent_forwarding=True。本方案用的是 tunnel=bastion_conn，目标机认证直接用本地私钥，私钥不经过跳板机。开启 agent forwarding 会让跳板机的 root 用户能借用你的 key。

审计日志

所有 exec、write_file、edit_file 操作写入本地 audit.jsonl，每行一条 JSON：

{"ts": 1727136000.0, "host": "dev1", "action": "exec",
 "detail": "cwd=/workspace cmd=git diff HEAD~1"}

known_hosts

内网机器经常重装，host key 会变。默认配置 known_hosts=None 跳过验证。如果内网 DNS / DHCP 稳定，建议改为指向一个独立的 known_hosts 文件，并在机器重装时手动更新。

直连节点不在跳板机后面，所在网络的可信度可能更低。对这类节点，建议通过 [host.x] known_hosts = "路径" 开启校验，尤其是使用密码认证的节点：不校验 host key 时，密码可能被中间人截获。

直连节点的凭据

直连节点的密码可以明文写在 config.toml 里。这个文件只存放在本机，并且已加入 .gitignore，仓库里只提交模板 config.example.toml，模板里全是占位值。password 字段留空时，改为启动时交互输入。认证失败不会自动重试，以免触发账号锁定。私钥和证书在配置里只写路径，文件本身留在本机。跳板机节点只用密钥免密登录，不涉及密码。

端口暴露

Daemon 仅监听 127.0.0.1:8765，不绑定 0.0.0.0，局域网内其他机器无法访问。

模块职责不做的事
pool.py维护 SSH 连接、处理断连重试、TOTP 交互不知道 MCP 协议，不知道工具语义
tools.py定义工具签名、参数校验、输出格式化、审计日志不直接持有 SSH 连接
daemon.py加载配置、注入依赖、启动 HTTP 服务不包含业务逻辑

8. 部署与接入

部署方案是"架构 A"：daemon.py 常驻在 Windows 本机，跳板机和目标 Linux 机器不需要安装任何组件，私钥始终留在本机。完整步骤见仓库里的 DEPLOY.md，这里摘录要点。

本机环境

Windows 上安装 uv（免管理员权限），要求 Python ≥ 3.10（推荐 3.11+：3.11 起 tomllib 是标准库，且本项目的超时/断线判定依赖 3.11 之后 TimeoutError 与 OSError 的继承关系）：

cd <REMOTE_MCP_DIR>   # 本机存放项目文件的目录，自选位置，不必是固定路径
uv venv --python 3.11
uv pip install -r requirements.txt
⚠
pywin32 postinstall 坑：mcp[cli] 在 Windows 上依赖 pywin32。如果用 pip install --target 等不经过标准 venv 安装流程的方式装依赖，pywin32 的安装后脚本不会被执行，运行时报 ModuleNotFoundError: No module named 'pywintypes'。uv pip install 装进真正的 venv 通常不会踩这个坑；如果遇到，手动补跑一次：& ".venv\Scripts\python.exe" ".venv\Scripts\pywin32_postinstall.py" -install。

config.toml 关键字段

仓库里只提交模板 config.example.toml（占位值，可以安全提交），首次部署先复制一份出来再改成真实值，config.toml 本身已加入 .gitignore，不会被提交：

copy config.example.toml config.toml

远端账号是 songjiajun，家目录是 /public/home/songjiajun（注意不是 /home/songjiajun）：

[daemon]
connect_timeout = 20   # 建连超时（秒），与命令级 timeout 参数是两回事，见第 5 节

[host.dev1]
user        = "songjiajun"
default_cwd = "/public/home/songjiajun"

如果有不经过跳板机、直接可达的目标机，用 via = "direct" 加一段直连节点，字段和认证方式见第 3.4 节：

[host.lab3]
via         = "direct"
address     = "192.168.10.23"
port        = 2222
user        = "songjiajun"
auth        = "key"          # key | password
default_cwd = "/public/home/songjiajun"

字段全表见第 7 节「config.toml 结构」。

密钥部署

把本机公钥追加到跳板机和每台目标机的 /public/home/songjiajun/.ssh/authorized_keys（目标机家目录同样是这个路径），并设好权限：

chmod 700 /public/home/songjiajun/.ssh
chmod 600 /public/home/songjiajun/.ssh/authorized_keys

私钥只留在本机，不上传、不复制到跳板机或目标机。via = "direct" 的节点不在跳板机后面，是单独一条 SSH 连接，需要把本机公钥额外追加到该节点自己的 authorized_keys（和跳板机、其它节点各自独立，不能共用一份）；auth = "password" 的直连节点不需要这一步。

启动 Daemon

# 在专用窗口启动，保持常驻
cd <REMOTE_MCP_DIR>
uv run daemon.py
⚠
daemon 启动时，此窗口会出现 TOTP 提示，输入一次后当次进程运行期间不需要再输入——除非调用了 reset_connections，或跳板机连接因网络问题被断开：这两种情况下，下一次工具调用触发重连时会再次在这个窗口阻塞式地提示输入 TOTP。因此这个窗口必须保持前台可交互（一个独立窗口或常驻标签页），不能扔进看不到输出、也没法输入的后台任务里，否则一旦触发重连，所有工具调用会一直卡住直到有人发现并回去输入。

如果某个 via = "direct"、auth = "password" 的节点没有在 config.toml 里填 password，daemon 启动时也会在这个窗口出现一次密码提示（如 [lab4] password:），交互输入最多允许试 3 次；直接写在配置文件里的密码只用一次，错了不重试、直接跳过该节点（不影响其它节点和跳板机继续启动）。网络不通或超时不会阻塞启动，会打印警告并留给后续调用时懒重连。

接入 Claude Code

claude mcp add --transport http --scope user remote-linux http://127.0.0.1:8765/mcp

--scope user 让所有项目都能用这个 MCP server，不需要每个项目单独配置。

接入 Codex

# ~/.codex/config.toml（新版支持 url）
[mcp_servers.remote-linux]
url = "http://127.0.0.1:8765/mcp"

# 旧版不支持 url 的，用 mcp-remote 做 stdio→HTTP 桥接
[mcp_servers.remote-linux]
command = "npx"
args    = ["-y", "mcp-remote", "http://127.0.0.1:8765/mcp"]

验证接入

> @remote-linux list_hosts
> @remote-linux exec(host="dev1", command="pwd")   # 预期返回 /public/home/songjiajun

排障

现象处理
daemon 窗口没有 TOTP 提示，卡住不动检查 [bastion] 的 host/port/user 是否正确；超过 connect_timeout 秒还没反应说明连接没建立，检查网络/防火墙
连接超时确认跳板机端口可达；适当调大 connect_timeout
触发 MaxSessions 限制sshd 默认单连接 10 个并发 channel，daemon 已对每台目标机限制 Semaphore(8)；仍触发则检查是否有其它进程占用同一条连接，或联系管理员确认 sshd 配置
提示 host 不在白名单[hosts] allowed 里补上（支持 fnmatch 通配符）
端口被占用改 [daemon] port，同步更新 claude mcp add / Codex 里的 URL
直连密码错误或被锁交互输入的密码最多允许试 3 次；写在 config.toml 里的密码只试 1 次，错了直接跳过该节点，不影响其它节点和跳板机。确认密码后改好 config.toml 或重启 daemon 重新交互输入
direct 节点连不上先确认 address/port 填得对、目标机可达（不经过跳板机，网络层面要直连得通）；如果是 PermissionDenied（密钥或密码错误）不会重试，需要改配置后重新触发连接；如果是网络不通/超时，daemon 只是记录警告并留给下次调用时懒重连，不会阻塞启动
✓
远端无需安装任何组件，也不需要在 /public/home/songjiajun 下建立服务目录——唯一的远端改动是 authorized_keys。

多跳板机

暂不支持并列多台跳板机；改动方案见仓库里的 TODO.md，此处不展开。

9. 风险与限制

风险影响缓解措施
Daemon 窗口被误关 所有工具调用失败，需重新启动并输 TOTP 可考虑用 Windows Task Scheduler 或 NSSM 将 Daemon 注册为后台服务；届时 TOTP 改为 TOTP secret 自动生成（需评估合规性）
跳板机长时间空闲被踢 连接断开，下次调用触发重连，需再输 TOTP keepalive_interval=30；如跳板机仍会踢，可在 Daemon 里加一个后台任务每 5 分钟跑一次无害的 echo keepalive
edit_file 写到一半进程崩溃 临时文件 .file.mcp.tmp 残留 原子 rename 保证目标文件要么是旧版本要么是新版本，不会有中间状态；残留 tmp 文件不影响原文件
模型生成危险命令（rm -rf 等） 远端数据损失 当前设计无命令黑名单（见后续增强）；生产机建议配置只读策略，不允许 exec
直连节点密码错误或被锁定 该节点不可用 认证失败不自动重试；交互输入的密码在启动时最多允许输错 3 次，写在配置里的密码错误则直接跳过该节点，都不影响其他节点；改好密码后重启 Daemon
Python 依赖版本冲突 Daemon 无法启动 用 venv 或 uv venv 隔离环境

10. 后续增强方向

以下功能不在 v1 范围内，列出供后续迭代参考：

  • 后台长任务：exec(background=True) 将命令放入 tmux 会话，返回 job_id；配合 job_status / job_output 轮询结果，适合编译和训练任务
  • 命令黑名单：在 exec 工具里拦截 rm -rf /、mkfs、dd if=/dev/ 等危险模式，记录告警
  • 只读模式：在 config.toml 里对特定主机开启 readonly = true，禁用 exec、write_file、edit_file
  • tail_log：实时追尾日志文件，支持关键字过滤，通过 SSE 流式返回
  • upload / download：通过 SFTP 传输二进制文件（core dump、模型权重等）
  • TOTP 自动填入：如果公司合规政策允许，将 TOTP secret 存入 Windows Credential Manager，Daemon 自动生成验证码，无需手动输入
  • Go 重写：用 golang.org/x/crypto/ssh 实现成单一 exe，分发给团队其他成员更方便
  • 多级跳板：目前 tunnel=bastion_conn 支持单跳；如果有二级跳板，可以在 pool 里把 tunnel 串起来：asyncssh.connect(target2, tunnel=target1_conn)
